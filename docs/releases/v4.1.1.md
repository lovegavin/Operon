# Operon Studio 4.1.1

Application 4.1.1 fixes the three upgrade-path defects found in 4.1.0 and keeps
the library requirement at **8.0.6 or newer**. The bundled operator library is
still 8.0.6 (7 packages, 1,171 descriptors, 4 isolated environments).

## Fixes

### Importing a library on an upgraded 4.0.x installation

`operon/source_library.py` now adds `operon/environments.json` to the source
fingerprint only when the file exists. Source trees created before 4.1.0 keep
their previous digest, so the "unrefreshed edits" check compares like for like
and no longer raises `FileNotFoundError` while unpacking a new library. Fresh
imports still record the manifest in the digest and copy it next to the
operators.

### Cross-platform bundle validation

`operon/library_bundle.py` verifies a bundle by comparing per-entry content
hashes (`wheel_contents`) instead of the whole-wheel sha256. Zip central
directory records differ between platforms (the "version made by" OS field and
case-sensitive path ordering), so a Windows-built bundle could never validate
on Linux and vice versa even though every payload byte matched. Manifest file
hashes and per-entry payload hashes are still verified.

### Missing environment manifest

An explicit library source that exists without `operon/environments.json` is
now reported as missing instead of silently falling back to the application
seed. `GET /api/environments` includes `manifest: {path, present}`, the library
panel shows a hint, and `environment_install.prepare` raises a clear
`FileNotFoundError` naming the library root.

### Environment installation is explicit

- Importing a library no longer starts environment installation. The import
  response reports the declared environments and their status only.
- Environment installation happens when the user installs dependencies during
  the pre-run dependency check (`POST /api/prepare-environment`, MCP
  `operon_workflow_prepare_environment`, `operon workflow prepare-environment`).
  Only environments used by that graph are prepared, together with their pip
  dependencies, and each operator is re-probed afterwards.
- `POST /api/environments/prepare` and `POST /api/environments/{name}/retry`
  remain available for manual preparation. New MCP tools `operon_environments`
  and `operon_environments_prepare` expose status and explicit installation;
  the prepare tool requires `--allow-plugins`.

### Desktop window behaviour

Minimizing Operon Studio keeps its taskbar button; only closing the window
hides it to the tray. The tray balloon explains that the workbench keeps
running and how to reopen or fully quit it.

## Compatibility

- Application 4.1.1 requires operator library **8.0.6+**; older bundles are
  rejected with an explicit version error.
- Wire protocol v3 and SDK 3.7 are unchanged.
- Saved workflow JSON, operator parameters and existing environments remain
  valid. Environments are reused when their receipt matches the manifest.

## Known limitations

- Preparing `openmm81` still needs a reachable package source and a compatible
  compiler for the pinned PDBFixer source distribution.
- The 4.0.2 workspace move is not an automatic data migration for existing
  4.0.x profiles.
