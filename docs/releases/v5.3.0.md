# Operon Studio 5.3.0

Candidate scope: automatic canvas RunPlan preparation and standalone export.
Publication is gated on exact Windows Setup and Linux package acceptance.

The original canvas Run and export entry points now compile the same frozen
RunPlan. They automatically collect native provider code, declared resources,
independent parameter JSON, scientific environments and conflict-specific
dependency targets. Preparation has bounded progress, cancellation and durable
status; a lost submission response does not cause a second scientific run.

Automatic environment capture covers private CPython, system-Python-derived
environments, Conda scientific prefixes, named Python environments, private R
runtimes/prepared R libraries and external tools in portable prefixes. Conda
relocation is performed once per final cache location. Repeated actions reuse
package receipts, preserving the package-level validation design.

The standalone package contains a small execution kernel, scripts, resources,
environment archives, `inputs.json`, `parameters.json`, and Windows/Linux run
scripts. It runs without an Operon installation on a compatible platform. Memory
admission, per-run partitions, spill, subprocess isolation and resume are retained.

This release also documents a six-session Tauri implementation plan. Tauri remains
a future experimental desktop shell; this release uses the established host.

## Boundaries

- The automatic native canvas route uses one execution host. Multi-host and Slurm
  features remain experimental; their promotion requires separate acceptance.
- OS ABI/GPU drivers, licensed applications and external services are not bundled.
- Arbitrary dynamic resources and unmanaged system executables require complete
  dependency declarations or a portable installation. They are not guessed.
- Existing headless legacy workflow endpoints remain compatible. They are not
  silently replaced by the canvas preparation API.
- Operator-library sources, seed packages and protocols are unchanged.
