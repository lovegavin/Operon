# Operon Studio 3.1.7

This is the current official Windows maintenance release. It keeps the 3.1.6
product names, the `2026.11.7.1` operator library and the existing v3 SDK
entry points, so saved workflows and operator identifiers remain valid.

## Remote build identity

The application, bundled library and installed catalog now produce one
deterministic `build_id`. A desktop and a managed server derive it from the same
source archive and library definition, so an SSH connection can prove that both
sides are identical before reusing a cached catalog.

Each managed installation records the identity in `server.json` and in the
environment receipt. Connecting to an older managed installation fails with the
stable `stale_build` code instead of silently reusing its catalog. The server
panel opens the existing maintenance flow and offers **安装 / 升级服务端**.

## Full operator-library replacement

The managed installer installs the library carried by the uploaded application
as one bundle. It replaces the complete built-in provider set; it does not merge
new wheels into an older registry and does not keep a stale provider that
disappeared from the new library. Source-edit protection is bypassed only for
this explicit managed replacement.

`library_manifest` reports the installed build and the per-operator
implementation digest. `library_check` reports `changed_count` and
`replacement_required`, and the remote library panel distinguishes
`implementation_changed` from a merely missing package.

## Execution pins

When the server build changes, `RemoteManager.prepare()` replaces a pin whose
operator implementation changed and records the previous pin as
`migrated_from`. A node whose operator is genuinely gone remains unavailable
with its operator ID; it is never silently deleted or rewritten.

## Windows desktop lifecycle

Closing the window hides Operon Studio in the Windows notification area, so a
running workflow keeps its local backend alive. The tray menu offers
**打开 Operon Studio** and **完全退出（停止 Python）**. A complete exit flushes
the draft, confirms running jobs when necessary, sends `shutdown` to the
backend, waits for the Python process and then closes the Job Object so no child
process survives.

The host removes legacy Operon/BioPipe login entries and Startup links at
launch; it never registers Python at login. If a version directory was removed
manually, the host repairs its Desktop, Start Menu and pinned taskbar shortcuts
to the running executable.

## Complete uninstall

The 3.1.6 uninstaller was a copy of the setup host that only honored an
explicit `--uninstall` argument, so launching it without that argument could
enter install mode. It also left the installation root in place and did not stop
the desktop host, whose backend could start a detached shared pool again.

The 3.1.7 uninstaller is selected by its filename, asks before terminating all
Operon Studio and Python processes, and runs itself from a temporary directory
so it can delete the root executable. `TerminateManagedProcesses` checks every
process image under the installation root, retries the termination, verifies
that no process remains, and reports the surviving PID and image if one does.
The uninstaller then removes the shortcuts, pinned taskbar entry, autostart
values and registry key, and deletes the installation root.

## Packages and validation

- `Operon_Setup.exe`: Windows installer with the bundled management Python.
- `Operon-Studio-v3.1.7-Windows-x64.zip`: the same complete payload without the
  setup wrapper.
- `Operon-3.1.7-Server.zip`: Linux installer, application wheel and the
  unchanged factory seed.
- `biopipe_studio-3.1.7-py3-none-any.whl`: application wheel for existing
  deployments.
- `biopipe_builtin_library-2026.11.7.1-py3-none-any.whl`: unchanged operator
  library wheel.

The focused build-identity, library-bundle, remote-installation and server
packaging regressions passed locally (90 passed, 1 warning in 272.26 s). The desktop host and installer compile
with zero warnings and zero errors. A silent install, a silent uninstall with a
running installed Python, and a registered install/uninstall were exercised on
Windows. The broader Windows Python suite was stopped before completion and is
not claimed as a pass. Published 3.1.6 tags and artifacts are unchanged.
