# Operon Studio 4.1.0

Application 4.1.0 ships **Operon Operator Library 8.0.6** and supports library
8.0.6 or newer only. Earlier libraries are rejected instead of being loaded with
an environment model this application does not provide.

## Environment manifest distribution

- An imported library bundle now carries `sources/operon/environments.json`
  under the same active source root as its operators.
- Environment lookup prefers the active imported library source and falls back
  to the application seed only when no imported manifest exists.
- Operators that declare `resources.environment` are routed through an
  `EnvironmentStep` proxy, so the declared Python version and packages are used
  instead of the shared runtime.

### Environment provisioning

- Importing a library bundle starts a background preparation job for every
  declared environment that is missing or stale; the import response is not
  blocked by package installation.
- Environments are created from the manifest under
  `library/sources/<id>/operon/environments.json` into the installation's
  `external/` root, with a per-environment lock, a staging directory and an
  atomic rename. A receipt records the manifest digest, so a changed spec is
  reported as `stale` and rebuilt.
- `GET /api/environments` returns each environment's Python version, status
  (`missing` / `stale` / `ready` / `failed`), the operators that need it and the
  last error. `POST /api/environments/prepare`, `POST /api/environments/{name}/retry`
  and `GET /api/environments/{name}/log` expose prepare, retry and progress.
- **算子库管理** shows an isolated-environment section with prepare, retry and
  log controls, so a missing environment is visible before a workflow fails.
- All dependencies are discovered from the operator-library bundle itself
  (`library.json`, `builtin_packages.json`, `environments.json`) and the route
  archive; the separate `install-dependencies.*` release assets are not
  required.

## OpenMM and PDBFixer

- The six structure operators that need OpenMM declare the `openmm81`
  environment and `openmm==8.1.1` + `numpy==1.26.4`.
- `openmm81` uses Python 3.11, installs PDBFixer 1.9 from the pinned upstream
  commit without build isolation, and keeps it in an isolated environment.
- This removes the previous `pdbfixer>=1.9` range, which could resolve PDBFixer
  1.12 against an OpenMM 8.2 wheel that the test mirror did not provide.
- The environment still needs a reachable package source and a compatible
  compiler for the pinned PDBFixer source distribution on the target host.

## Included 4.0.10 fixes

- Windows Setup uses the exact selected folder, records the installation root,
  asks for **强制重装** for an older root, and removes everything except
  `workspace` on uninstall.
- Remote submissions clear stale plugin pins from an older canvas before
  preparing against the selected server.
- Forced server upgrades close every remote workspace session; normal upgrades
  still abort on active work.

## Compatibility

- Application 4.1.0 requires operator library **8.0.6+**.
- Wire protocol v3 and SDK 3.7 are unchanged.
- Saved workflow JSON and operator parameters remain valid.
