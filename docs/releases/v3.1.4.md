# Operon Studio 3.1.4

This application patch fixes workflow/library import compatibility, cooperative
SSH server upgrades, and the separation of environment checks from execution
preflight. The operator library is independently versioned; this release does
not replace the factory library or change the operator protocol.

## Workflow and library imports

- Both workflow import and Add operators accept `.operon` and `.operon.zip`
  bundles, alongside existing Operon bundle names. Frozen parameter and execution
  sidecars accept the corresponding Operon and Operon format identifiers.
- Current `.operon-library.zip` archives and the seven renamed official providers
  are recognized. Disabled package state and retained snapshots are preserved.
- Source-to-wheel pins are translated only after verifying the same implementation
  bytes. Matching a name or version alone never authorizes a replacement.
- Passing a library archive or an outer collection of routes to the single-route
  importer produces an actionable error. Ambiguous input Readers require an
  explicit selection instead of silently choosing a format.

See [import compatibility](../library_import_compatibility.md).

## Server upgrades

Explicit installation or upgrade asks an idle earlier server to retire before
starting the replacement. Normal connections continue to reuse a compatible
installed server. Active jobs, transfers and maintenance block retirement; they
are not killed and their resource reservations are not discarded.

Shared-pool admission conflicts retain the conflicting launcher information.
Servers predating cooperative retirement may require a one-time stop after their
jobs finish, followed by reconnecting and retrying the upgrade. The client reports
this condition instead of forcibly taking ownership of a live allocator.

## Separate checks and explicit preparation

Execution settings now contain **Environment dependencies** and **Run preflight**.
The first checks the selected execution hosts, operators, Readers and tools without
requiring input data paths or starting the shared resource pool. Missing dependencies
have an explicit installation action. The toolbar check opens the same panel, so
an unsuccessful check has a visible explanation and recovery action.

Run preflight still validates graph connections, frozen parameters and required
input/reference files. Successful dependency checks can be reused while the
declarations, selected environment and dependency state remain valid. Failures
are not cached. Preparation and environment changes invalidate the relevant
receipts; a dependency-only success never substitutes for complete preflight.

The same boundary is available through CLI `environment check`, API
`/api/v1/workflows/check-environment`, and MCP
`operon_workflow_check_environment`. CLI `--require-files` requests full preflight.
See [readiness](../readiness.md) and [server CLI](../server_cli.md).

## Distribution and validation

- `Operon_Setup.exe`: Windows installer with a private management Python.
- `Operon-3.1.4-Server.zip`: Linux server installer, application wheel, unchanged
  independently versioned factory library, and English documentation.
- The application wheel is provided separately for existing Python deployments.

Scientific environments remain explicitly prepared for their selected execution
hosts. Existing memory management, spill behavior, frozen parameter JSON, and the
automatic shared pool remain enabled. Release-page verification records distinguish
source tests, packaged checks, and actual desktop acceptance for the delivered bytes.
