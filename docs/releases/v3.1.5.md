# Operon Studio 3.1.5

This application update adds server operator-library checks and selected package
transfer, and fixes cooperative Windows updates. The independent operator library,
scientific environment versions and operator protocol are unchanged.

## Server operator library

Connecting to a server automatically compares the local and remote registered
operators and Readers. Settings > Servers also provides **Check library** and a
selectable list of missing packages. Comparison reads registry documents without
importing operators, scanning their implementation trees or repairing dependencies.

Select the packages to supplement, then choose **Install selected**. Transfer uses
the existing checksummed, resumable upload store and reports package/byte progress.
The server validates the selected revisions and installs one immutable registry
generation. Rechecking confirms the result. Adding provider code does not install
scientific dependencies; use Environment dependencies for the selected runtime.

Provider packages are the installation unit. The interface discloses replacement
counts. Disabled providers, ownership conflicts and changes that would discard
remote-only operators are blocked. A changed registry requires a fresh check;
platform-specific wheels require a compatible server build. Older servers can be
compared but must be explicitly upgraded before using package supplementation.
Route operators remain saved workflow documents, not transferable provider code.

See [server handshake and library synchronization](../SERVER_HANDSHAKE.md).

## Windows updates

Updating an existing managed installation now asks its idle Studio windows to
close normally, waits for their processes to exit and protects the old profiles
through the installation transaction. A failed close leaves the previous
installation intact and can be retried in the same Setup window.

Active jobs, foreign clients and unresponsive windows still block replacement;
Setup never kills arbitrary Python processes or discards running work. Installing
in a separate directory does not close a different installation. The shared pool
breaks away from the desktop process container so that closing one desktop cannot
terminate another client's running work.

See [Windows Setup](../windows_setup.md).

## Packages and validation

- `Operon_Setup.exe`: Windows installer with the existing private management Python.
- `Operon-3.1.5-Server.zip`: Linux installer, application wheel and unchanged factory seed.
- `biopipe_studio-3.1.5-py3-none-any.whl`: application wheel for existing deployments.

Frozen workflow parameters, memory admission, spill and streaming remain enabled.
Release attachments record the focused tests and packaged/native acceptance for
these exact bytes. Source tests do not imply all scientific operators were tested.
