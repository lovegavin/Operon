# Operon 5.2.0 final-package acceptance

Use only the candidate named in the accompanying checksum manifest. This is a
release gate, not authorization to publish from the test computer. Record failures,
skips and untested scenarios separately. Do not replace failed package checks
with source-checkout results. Multi-node placement and Slurm remain experimental.

## Protect existing installations

Use a new evidence directory and a new installation directory. Record existing
Operon shortcuts, installation registrations, global runtime settings and selected
old profile hashes. Keep previous installations, profiles, provider wheels, system
Python and editor settings. Never clean old evidence to make a test pass.

Verify the outer ZIP SHA256, extract the whole ZIP, then verify SHA256SUMS.txt and
Operon_Setup.exe.sha256. Keep FORWARD_TO_TESTER.txt with the package. Record the
actual installed application version, private Python and profile/workspace paths.

## Windows interactive acceptance

1. Actually double-click Setup and install into the new directory. Launch through
   its shortcut, not a developer server. Confirm version 5.2.0. Record startup and
   normal shutdown, then reopen through the shortcut. Do not disable automatic
   checks to bypass a failure. No preconfigured analysis Python is required.
2. Install an unchanged compatible operator-library release separately if the
   synthetic PCA route needs it. Record that library's version and SHA256; never
   rebuild or modify its operators as part of this application test.
3. Follow scripts/verify_release_agent.md with `--version 5.2.0` in every phase.
   Explicitly authorize route-only environment preparation for the backend phase.
   Complete the real PCA selection, batch edit, single undo and restart/retry
   phases. Check actual canvas edits and selection, not only API responses.
   Reopening/retrying must reuse the original task rather than create a duplicate.
4. In run history, open original PNG, PDF and SVG results. Verify each visible
   figure and original file separately. Do not count a preview thumbnail as an
   original-file open. Existing third-party viewer handoffs remain separate tests.
5. In Settings, exercise configured storage root listing, directory navigation
   and bounded preview. Select a local synthetic file into an input node. Save,
   reopen and verify that the saved source retains its StorageRef. Run it only
   with an existing authorized execution input root. Change the selected file
   after saving: execution must reject the stale version until deliberately
   reselected. Do not broaden input roots implicitly to make the test pass.
6. Exercise the separate RunPlan panel using the supplied prepared fixture and
   its generated binding instructions. Compile/import without starting a task;
   choose a verified environment, inspect frozen parameters and submit explicitly.
   Close/reopen the panel and Studio: the original submission must remain visible.
   Poll status, attempts, events and logs; inspect original committed artifacts.
   An explicit same-request retry must reuse the original run. Do not construct
   a second request ID to resolve a lost response. Check cancellation on a fresh
   long-running synthetic plan and confirm owned processes stop.
7. Export the fixture's portable plan with its supplied manifest. Inspect the
   durable export receipt, relocate the resulting directory, and run its target-
   native launcher independently of the Studio session. Compare numeric results.
   A Windows package does not prove Linux or arbitrary R/native environments work.
8. Reinstall through Setup while Studio is open and follow its shutdown prompts.
   Confirm safe owned-process shutdown, a working new shortcut and preserved old
   profiles. Uninstall only this candidate through Windows. Verify old baseline
   hashes and registrations; record retained caches rather than deleting them.

The fixture preparation step is explicit and executes only trusted synthetic code
with a private copied environment. Never substitute developer-generated hashes,
unverified dependency directories or a different release's fixtures.

Run the delivered helper with the actual installed private Python and workspace:

```powershell
& '<installed-private-python>\python.exe' '<installed-code-root>\scripts\acceptance\prepare_desktop_plan.py' --application-root '<installed-code-root>' --workspace '<installed-workspace>' --python-home '<installed-private-python>' --prepare-environment
```

The helper creates an isolated `desktop-plan-acceptance` fixture, verifies its
copied runtime and emits compile-request.json, execution-plan.json, binding.json
and export-request.json with real computed identities. Its two-stage synthetic
JSON workflow produces 14 then 42. Follow the generated fixture instructions;
import its compile request in the RunPlan panel and its generated binding rather
than typing generation IDs. Do not rerun preparation over existing evidence.
The helper does not install or alter an operator library or the original runtime.

## Linux exact-archive acceptance

Use a fresh server directory and the delivered Operon-5.2.0-Server.zip. Verify its
outer SHA256 and inner SHA256SUMS. No second node or Slurm is required. Run:

```sh
bash install.sh --prefix "$HOME/operon-520-acceptance/install" \
  --result "$PWD/server-install.json"
```

Use the actual `command`, `python` and `workspace` from server-install.json, not
an assumed install path. Check `--version`, `service status`, registered server
handshake and installed module locations. The package installs the application
only; scientific libraries are a separately recorded explicit action.

Copy examples/workflows/script_pipeline into the selected workspace. Perform
environment check and explicit prepare if necessary, then run workflow.yaml with
`--progress --brief`. Preserve frozen parameter JSON and logs. Re-run/retry as
documented and verify task identity, cancellation and owned-process shutdown.
Run the supplied RunPlan fixture through the installed CLI and ordinary shared
host pool; inspect results and portable export from the installed application.
Reinstall into the same owned prefix and verify preserved workspace and an
intact previous runtime on failure. Stop the owned service after testing.

Report exact commands, package/environment identities and evidence paths. Real
SFTP/SSH transport is a separate acceptance item: a provider's browser terminal
does not prove an SSH gateway or SFTP transport works. Do not claim multi-host,
Slurm, failover or arbitrary scientific dependency qualification.

## Report

Provide a table for each item with passed/failed/skipped, observed behavior and
evidence. Include Setup/install timings, normal exit codes/times, library identity,
Python identity, task IDs, preserved baseline hashes, remaining owned processes,
and an evidence ZIP SHA256. Never include authentication tokens or passwords.
The release owner compares both exact-package reports before publishing.
