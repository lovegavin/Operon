# Operon Studio 4.2.4

- Application: **4.2.4**
- Built-in operator library: **8.0.10**
- Minimum supported library: **8.0.10**

## Binary workspace writes

Agents can now write PNG, PDF, ZIP or any other binary payload through the
backend, without host filesystem permission inside the workspace:

```text
operon_write_binary(path="task1/figures/chart.png", content_base64="iVBORw0...")
```

- `POST /api/v1/workspace/files/binary` with
  `{"path": "...", "content": "<base64>", "overwrite": true}` is the HTTP form.
- `content_base64` is standard base64; data-URL prefixes are rejected.
- Decoded payloads are limited to 50 MiB; UTF-8 text writes stay at 10 MiB.
- Path rules are unchanged: workspace-relative, no `..`, no absolute paths, no
  symbolic links, and no Operon internal state (`.studio`, `.operon`,
  `.admission`).
- New capability: `workspace-binary-files`. Text writes remain under
  `workspace-files`.

## Remote preparation diagnostics

Two failure messages now say what to do next:

- A pinned implementation that is unavailable on an SSH target names the host
  and points at `operon_remote_install(force=true)`. The most common cause is a
  server whose operator library differs from the workspace.
- A missing input file on an SSH target explains that Operon uploads files that
  are referenced from a local source; a file that only exists as a remote path
  must be copied into the server workspace first.

Remote force upgrade was already available through MCP as
`operon_remote_install(profile_id=..., force=true)`; 4.2.4 only makes the
diagnostic point at it explicitly.

## Operator library 8.0.10

The built-in library is **8.0.10** and the minimum accepted version is now
**8.0.10**. This release uses the library whose 1,171 descriptors carry
consistent `code_sha` values, so a local and an upgraded remote server can
validate the same pins.

Older libraries are rejected at import with `version 8.0.10 or newer is
required`.

## Compatibility

- Library 8.0.10 declares `minimum_application: 4.2.2`; Studio 4.2.4 accepts it.
- Workflows saved under 4.2.2/4.2.3 remain readable; route pin migration keeps
  the 4.2.3 rule: rewrite only provable pins, reject anything else explicitly.
- The 4.2.4 Windows installer keeps the 4.2.x installation model: the selected
  directory is the installation root, existing versions are replaced, and
  `workspace` is preserved.

## Validation

- Focused Python suites for workspace writes, task folders, pin migration,

- Frontend type check, Vite build and Vitest suite.
- Windows install, startup, MCP handshake and binary-write probe.
