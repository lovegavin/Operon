# Operon 3.1.1 — automatic shared-pool scheduling

Desktop, CLI/API/MCP and SSH server workspaces now automatically use the shared
resource-pool coordinator. No pool command, address or token is needed for the
ordinary local or server workflow. Upgrade both the desktop and execution
server to enable this default on each host; installing a desktop does not replace
an already installed remote server.

## Behavior

- Concurrent clients in the same host/account admission domain discover one
  detached pool. There is one RAM/CPU authority across their workspaces.
- Each workspace retains its own task files, frozen parameter JSON, selected
  interpreter, allowed input roots and artifacts. Scientific environment
  preparation remains explicit and follows the chosen workflow target.
- Closing or losing a client does not cancel accepted pool workers. When no
  clients, tasks or leases remain, the automatic pool exits. Pending stages of
  a closed workflow orchestrator remain resumable on reopening/retry.
- A crashed pool is restarted and surviving workers are adopted without a new
  launch. Active attempts retain the original capacity snapshot. A cold start
  after all attempts drain scans capacity again.
- `operon pool status` inspects the account-local pool without starting it.
  `operon pool stop` retires an idle pool and refuses active work.
- Startup, version conflicts and live legacy ownership fail explicitly; they
  never silently create another allocator. Finish old tasks and close old
  clients before switching versions. An explicit legacy mode remains available
  for diagnosis on a drained admission domain.

## Additional repairs

Job details and remote event queries now use the pool's authoritative lifecycle
record. Reconnected subscriptions are correctly removed when clients close.
Linux zombies are recognized as exited processes. Dynamic workspace bindings
are serialized and persisted before their registration is acknowledged.
Headless routes without canvas coordinates are normalized consistently, and
idempotent submission replies retain their `reused` flag. Workspace catalog
discovery policies are preserved so metadata-only clients do not continuously
invalidate source-aware clients' cache generations. Windows long-path artifact
verification is supported; downstream stages wait for publication and fail
explicitly when publication fails.

The factory library and SDK version are unchanged. Windows Setup retains the
lightweight bundled management Python. No new scientific dependencies are
installed at application startup.

See [pool deployment and lifecycle](../design/pool_service.md). This does not
introduce immutable environment generations, hostile multi-user isolation, or
production Reader streaming. Verification for this build is recorded separately
from the previous 3.1.0 explicit-pool acceptance.
