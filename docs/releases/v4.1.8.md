# Operon Studio 4.1.8

4.1.8 makes replacing an installation a single, complete operation and gives
every client a way to inspect and stop a shared pool. It still requires
Operator Library 8.0.6 or newer and now ships 8.0.7 as the built-in library.

## Operator library 8.0.7

- The built-in library is **8.0.7**, with the same 1,063 operators, 108 Readers,
  1,171 descriptors and 79 routes.
- `openmm81` now uses Python 3.12 (the shared host interpreter) and pins
  `setuptools<81`; its probe imports `pkg_resources`, fixing OL-01
  (`No module named 'pkg_resources'`). PDBFixer remains pinned to the upstream
  commit and built without build isolation.

## Full replacement on install and upgrade

Installing or upgrading now always disconnects every local agent, clears the
shared pool, removes the previous versions and only then unpacks the new
build. If the pool still owns active tasks, Setup asks whether to force the
update; forcing it cancels that work and deletes the pool state, so the next
launch starts from a clean environment.

- The previous build is deleted before the new one is extracted; no version
  directory, uninstaller or registration entry survives the switch.
- `workspace` is preserved, together with the user profile and logs.
- `--force` performs the same clean replacement without the confirmation.
- `<install root>\bin` provides stable `python.cmd`, `operon.cmd` and
  `operon-studio.cmd` entry points.
- A pool that is merely idle is retired normally; no prompt is shown.

## Pool control from MCP

Three tools expose the shared pool:

- `operon_pool_status()` — local pool version, owner, workspaces and tasks.
- `operon_pool_stop(force=False)` — stop the local pool; `force=True` cancels
  its active tasks and removes the pool state.
- `operon_remote_pool_stop(profile_id, force=False)` — the same operation on a
  connected server.

The desktop forwards both through `/api/pool/stop` and
`/api/remote/<profile>/pool/stop`; the runtime status panel gained matching
buttons with an explicit confirmation before anything is cancelled.

## Remote isolated environments

The remote RPCs added in 4.1.7 (`environments`, `environments_prepare`,
`environments_log`) were unreachable because their dispatch branches were
nested under the `pool_info` return. 4.1.8 fixes the dispatch so
`operon_environments(profile_id=...)` and
`operon_environments_prepare(profile_id=...)` act on the selected server.
The desktop also adds the missing `/api/agent/remote/*` proxy, so these
requests reach the selected server instead of being handled locally.

## Validation

- Focused Python suites cover pool stop/force-clear, remote environments and
  the library/environment contracts.
- Frontend: 177 tests and a production build.
- Windows install, upgrade, MCP handshake and uninstall are exercised against
  a real installation on this machine, including a full replacement of an
  older build in the same directory.
