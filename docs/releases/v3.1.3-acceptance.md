# Operon 3.1.3 desktop acceptance

Use the exact `Operon_Setup.exe` and SHA256 published with the candidate. Do not
substitute an earlier installer. Keep previous installations, profiles, provider
wheels, runtime configuration and evidence intact. Record the chosen installation
and profile paths, application version, actual Python, and each exit code.

## Installation and basic use

1. Double-click Setup and install into a new independent directory. Launch the
   installed shortcut. Confirm version 3.1.3, the private management Python, and
   a new profile. Keep explicit environment preparation enabled.
2. Create a small synthetic CSV-to-PCA graph. Save it, close the app normally,
   and reopen through the shortcut. Verify the saved graph and record shutdown
   duration and backend exit code. Check the previous global `runtime.json`
   remains byte-identical.

## Import compatibility

1. Export the connected graph as a workflow bundle. Import copies named
   `sample.operon.zip` and `sample.operon` through File / Import workflow.
   Verify nodes, edges, frozen PCA parameters and execution settings.
2. Use Add operators / Workflow operator to register the same bundle. Confirm
   it appears in the library and can be inserted into a new canvas.
3. In an isolated test profile, install the official library-v6.0.1 Windows
   `.operon-library.zip` archive. Verify the seven providers, 1,017 operators and
   108 Readers. Import a single nested `.operon.zip` from the matching routes
   collection through both entrances. Do not submit the outer collection as
   a single route; that must produce a useful error.
4. Preserve the original library and route archive hashes. A route that requires
   an explicit Reader choice must explain that choice; do not weaken validation
   or clear plugin locks to make it import.

## Environment checks before input data

1. On a new connected CSV-to-PCA graph, leave the input path empty and explicitly
   choose `CsvReader`. Open Execution settings / Environment dependencies.
   The check must reach dependency results without requiring the file.
2. With a missing scientific dependency, confirm an installation action is
   visible. Click it only for the selected test environment. Confirm successful
   preparation changes dependency status to ready without starting a task.
3. Run preflight while the path is still empty: it must fail on the input. Fill
   in the synthetic CSV path and retry: it must check the complete graph and
   reuse valid dependency results. A missing file or disconnected required
   operator input must still fail.
4. Trigger the top-right check on an unready graph. Execution settings must open
   with a persistent error/status and the same preparation action where relevant.
5. Change the selected execution environment or operator dependencies. The old
   ready result must not authorize the new environment. Recheck explicitly.

## Core agent regression

Follow the installed `scripts/verify_release_agent.md`, using `--version 3.1.3`.
Confirm a real selected node, a visible batch modification, one-step undo, and
reopening/reusing the original task. Record separately any stages that were not
actually exercised. Scientific dependencies may be installed only into the
explicitly selected test analysis environment.

## Server boundary and final report

Desktop testing alone does not prove SSH deployment. The server-specific tests
must separately cover idle cooperative retirement, refusal while jobs/transfers
or maintenance are active, ownership conflict details, normal compatible-server
reuse, and the Linux installer/package checks. Never kill an active old server
or discard its admission ledger to make an upgrade pass.

Report observed passes, failures and untested items separately. Preserve screenshots,
desktop logs, dependency records and the candidate SHA256. Restore any temporary
shortcut/registration changes. Do not publish the candidate from the test machine.
