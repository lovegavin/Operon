# Operon Studio 4.1.4

4.1.4 fixes the MCP entry point shipped with the Windows application runtime.

## What was wrong

The packaged runtime in 4.1.3 still carried `operon` 3.1.8 inside
`runtime/python/Lib/site-packages`. The desktop host worked because it starts
the backend from the version directory, but an MCP client launches
`python -m operon ...` from its own working directory. That import resolved the
old 3.1.8 package, which rejected the 4.1.x workspace profile and exited before
the MCP handshake. The bundled `operon.cmd` uses isolated mode, so it printed
`Operon 3.1.8` as well.

## What changed

- The runtime now contains the matching `operon` / `operon_sdk` / `src` code and
  an `operon_studio-4.1.4.dist-info` record; the stale 3.1.8 packages and
  metadata are removed.
- `scripts/package_release.py` refuses to package a runtime whose
  `site-packages/operon/__init__.py` version differs from the application, or
  whose distribution metadata is missing or duplicated.
- `operon.cmd --version` and `python -I -m operon --version` now report the
  installed version from any working directory, so the MCP configuration shown
  in the Agent panel resolves the current code.

## Compatibility

- Operator library 8.0.6 or newer, as in 4.1.x.
- No wire-protocol or SDK change.
- Existing workspaces and profiles remain valid; this is a runtime-content fix.

## Verification

- Fresh Windows install: `operon.cmd --version` reports `Operon 4.1.4`.
- MCP `initialize` + `tools/list` succeeds when the client starts the configured
  Python from a directory outside the installation.
