# Operon 5.4.8 → 6.0.0：Rust/Tauri 宿主迁移交接

状态：规划交接（2026-11-17）。基线是已发布的 **Operon Studio 5.4.8**（`v5.4.8`，
release `448812716`，提交 `24778beff`），目标是把 Windows 桌面宿主从
C#/WinForms + WebView2 换成 Rust/Tauri，应用版本进入 **6.0.0**。迁移只换宿主壳：
Python 管理服务、RunPlan 与调度、环境隔离、参数 JSON、算子库、科学 SDK 全部不动。

## 1. 结论先说

- 现成的实验分支 `experimental/tauri-shell` 已经做完了宿主替换的主要部分：
  Rust 宿主进程生命周期、Windows Job 所有权、认证 artifact 打开、原生对话框、
  安装器（C#）+ 维护命名管道、RC1–RC8 的一串修复，以及 104 个文件、26,280 行新增。
- 但它的基线是 **5.3.0**，不是 5.4.8；且它自己还没有过“独立机器上的完整 UI 门禁”。
- 因此 6.0.0 的第一件事不是写 Rust，而是把这条分支 rebase/移植到 5.4.8，
  再按“开发版直跑 → 打包 → 装机/升级/卸载 → 第二台机器”的顺序逐门禁推进。

## 3. Rust 技术栈（复述）

`desktop-tauri/Cargo.toml`：package `operon-desktop-experimental` 0.1.0，edition 2021，
`rust-version = "1.100.0"`；lib `operon_desktop_experimental`；bin
`operon-desktop-experimental`，`required-features = ["desktop"]`。
`rust-toolchain.toml` 固定 **1.100.0**（minimal + rustfmt + clippy），`Cargo.lock`
（5,669 行）已提交。

- 桌面框架：`tauri = "=2.12.5"`（`tray-icon`），`tauri-build = "=2.7.4"`。
- 异步与进程：`tokio 1`（process / io-util / time / rt-multi-thread / sync / macros / net）。
- 序列化与网络：`serde` + `serde_json`，`reqwest 0.12`（json + rustls-tls，无默认特性），`url 2`。
- 其他：`uuid 1`（v4）、`fs2 0.4`（文件锁）、`sha2 0.10`、`rfd 0.15`（原生对话框）、
  `open 5`、`keyring 3`（windows-native）。
- Windows 原生：`windows-sys 0.61`（Foundation / JobObjects / Threading / Pipes /
  Security / UI_Shell / UI_WindowsAndMessaging / System_Diagnostics_ToolHelp）。

`tauri.conf.json` 的关键取舍：`build.frontendDist = "ui"`（只是一个静态加载/诊断外壳），
`app.windows = []`（窗口运行时创建），`security.capabilities = []`（能力在运行时绑定到
**真实后端 origin**），CSP `default-src 'self'; connect-src ipc: http://ipc.localhost;
img-src 'self' data:; style-src 'self' 'unsafe-inline'; script-src 'self'`，
`bundle.active = false`（打包走自己的 Setup）。

IPC 命令只有六个：`ready`、`acknowledge-draft-flush`、`show-diagnostics`、
`request-full-exit`、`open-committed-artifact`、`select-path`（`permissions/host.toml`
的 `host` 集合）。**没有 fs/shell 插件权限**，也不允许 localhost 通配或任意远程页面。

## 4. 生命周期不变量（迁移不能丢语义）

1. Python 以 **挂起** 方式创建，先归入自有 **Windows Job Object**，再 resume；
   就绪必须证明“该进程或该 Job 的成员”（含 Windows venv 的 redirector），
   然后做实例密钥 challenge 与 bootstrap 校验。
2. 关窗只隐藏；托盘/菜单 `Quit Operon` 先请求草稿保存，再停自有管理树。
   **不取消远端/共享池任务，不按名字杀无关 Python。**
3. 草稿超时恢复窗口；drain 超时保留所有权并可重试；非零退出即使重试成功也算失败；
   显式关闭失败树时宿主以 exit code 1 退出。
4. `RunEvent::ExitRequested` 只在 `bridge::exit_is_verified(app)` 为真时放行。
5. 同 profile 第二次启动是 **拒绝**（安全），而不是激活既有窗口——这是已知限制。
6. 配置 `host.example.json` → `host.local.json`：`installation_id`、`backend_root`、
   `python`、`frontend`、`profile` 五个字段，`deny_unknown_fields`，相对路径按配置文件
   所在目录解析，**没有 PATH 搜索、没有全局运行时回退、不迁移生产 profile**。

## 10. 建议的 6.0.0 路线（按门禁推进，不要跳）

**阶段 0：把分支接到 5.4.8**

1. `git rebase --onto release/5.4.0 0600b2bba experimental/tauri-shell`，冲突主要在
   `operon/`、`frontend/`、`scripts/`、`docs/`。
2. 保留 5.4.8 的行为：调色板单一来源、`librarySource` 下拉、圆圈按钮=重新读取、
   路线库按 id 解析（`strip_pins`，pin 只进 manifest）、基础库首启安装、宿主启动上限。
3. 产物自检：`cargo build --locked`、81 单测、12 进程测试、前端 240 tests。

**阶段 1：宿主对齐 5.4.8 行为**

- 版本显示：`/api/version`、`/api/bootstrap.studio`、页脚与应用信息都读同一份
  `installation.json`/版本目录名，不再各自 import `package.json`。
- `librarySource` 切换、`route-collections` 卸载、`/api/route-collections` 全链路在
  原生宿主下再点一遍（这些是 5.4.7/5.4.8 才有的）。
- 补 `desktopHost` 适配层（browser/WebView2/Tauri），把窗口相关调用收口。

**阶段 2：开发版直跑验收**

`cargo run -- --config host.local.json`，用真实安装目录的 `runtime\python.exe` 与
`frontend\`（扁平 `index.html`），逐项过：ready、草稿保存、隐藏/显示、Quit drain、
artifact 打开、原生 picker、凭据、旧图 handoff。

**阶段 3：打包与装机**

- 用 5.4.8 payload 当输入，`package_tauri_experimental.py` 换壳；确认 `.pyc` 缓存失效、
  manifest 逐文件哈希、footer 正确。
- 安装 → 首启 → 导入库/路线 → 连服务器并强制升级 → 跑一条真实路线 → 升级 → 卸载；
  每步留哈希与时间。**装机终验由用户执行。**

**阶段 4：第二台机器 + 生产化**

- 在无 Rust/Node/开发 Python 的干净机器上双击安装，验证 bundled management Python。
- 决定 6.0.0 的安装根与身份：建议 **保留独立根**（`%LOCALAPPDATA%\Programs\Operon Studio`），
  不覆盖 5.x 安装目录；`productName`/`identifier`/注册表键都要换回生产语义。
- 签名、更新器（当前没有）与回滚策略在 6.0.0 前补齐或明确声明不支持。

**阶段 5：6.0.0 发版**

版本号（`pyproject.toml`、`operon/__init__.py`、`frontend/package.json`+lock、
`desktop-tauri/Cargo.toml`、installer csproj）统一 6.0.0；`docs/releases/operon-6.0.0.md`；
四资产（Setup/Server/wheel/SHA256SUMS）进本地交付目录；tag + 直连推送 + 发布 latest。

## 11. 已知坑（都是踩过的）

1. **`\\?\` 扩展路径**：用带前缀的路径启动 Python 会让 `sys.prefix` 也带前缀，
   OpenMM/原生扩展找不到 DLL。统一走 `operon/python_paths.py` 的规范化。
2. **`.pyc` 缓存**：payload 里带 `UNCHECKED_HASH` 字节码会让宿主继续执行旧模块；
   换壳脚本必须失效被替换 overlay 的缓存。
3. **`desktop_server.py` 在 stdin EOF 时自动关停**：后台/计划任务方式起服务会
   “startup complete → Shutting down”；要用 `Popen(..., stdin=PIPE)` 持有管道。
4. **首启基础库安装耗时**：5.4.7 起宿主上限 300 s；Rust 宿主用的是就绪握手，
   必须确认它不会在库安装期间误判超时。
5. **安装器身份隔离**：实验安装根、卸载键、快捷方式都带 installation id；
   6.0.0 换回生产身份时不要误删实验安装，也不要让两者互相覆盖 profile。
6. **打包审计**：`package_release.py` 会拒绝含开发者路径的文档；版本号要三处同步。
7. **PowerShell 5.1**：`Invoke-WebRequest` 非交互不可用、`-Encoding utf8` 会写 BOM、
   原生命令的 stderr 会被当 `NativeCommandError`（假失败）。
8. **同 profile 二次启动**：当前安全拒绝，用户会以为“程序没反应”，6.0.0 应改成
   “转发到既有窗口”。

## 15. 能不能“只换技术栈、功能与发行形式不变”

结论：**能，而且这是成本最低的路径**，但要先把三件事从“换壳”里拆出来。

### 15.1 天然不变的部分（不需要动）

宿主管的是窗口、启动、生命周期、OS 服务与安装维护；5.4.8 的功能逻辑都在 Python
管理服务与前端里：调色板单一来源、`librarySource` 下拉、圆圈按钮=重新读取、路线库
按算子 id 解析（`strip_pins`）、基础库首启安装、多库管理、版本显示、远程强制升级、
共享池与准入。只要 payload 用 5.4.8 原样，这些行为天然保留。

### 15.2 必须对齐的三件事

1. **打包常量与 overlay 清单**。`package_tauri_experimental.py` 目前硬校验
   `MANAGEMENT_RELEASE = "5.3.0"`：`package-manifest.json` 的 `version` 必须相等、
   `python_bundled` 必须为真、逐文件 size/sha256 必须与 manifest 完全一致，还要求
   `runtime/python/python.exe` 与 `scripts/desktop_server.py` 存在；然后删除
   `PRODUCTION_WRAPPERS`（`Operon Studio.exe`、`operon-desktop.json`、`START_HERE.txt`、
   `operon.cmd`、`package-manifest.json`、`Operon_Setup.exe`、`Operon_Uninstall.exe`）
   与所有 `*.lnk`，再放入 Rust 宿主。对齐 5.4.8 即改常量、确认 5.4.8 payload 的实际
   文件名与清单一致，并保证 `library/base/*.operon-library.zip` 被保留且完整哈希。
2. **安装身份与根目录**。实验版是 `Operon Studio Experimental` +
   `%LOCALAPPDATA%\Programs\Operon Studio Experimental` + `OperonStudioExperimental-<id>`；
   发行形式要一样，就得换回 5.4.8 的产品名、默认根、快捷方式名、卸载键，同时保留
   `versions/<build-id>`、`profiles/<installation-id>` 布局与“profile 升级/卸载都保留”。
   这一步决定用户看到的是不是同一个产品。
3. **宿主行为对齐**。Rust 宿主必须复刻 C# 宿主的可观察行为：ready 握手与首启基础库
   安装（5.4.7 起给了 300 s 余量）、关窗隐藏、Quit 先存草稿再停自有进程树、强制升级前
   先断开 agent（5.4.2/5.4.3 语义）、同 profile 二次启动的处理（Rust 版目前安全拒绝，
   用户会以为没反应；5.4.8 是激活既有窗口）。

### 15.3 不建议一起换的

安装器（`desktop-tauri/installer/*.cs`，约 2,900 行）、维护命名管道、卸载器与自检目前
都是 C#，且已过 RC3 的安装/升级/卸载验收。6.0.0 应沿用这套安装器、只换它铺下去的宿主
二进制；把安装器也改写成 Rust 属于第二阶段，会同时引入签名、维护协议与回滚风险，
不应与 6.0.0 的首要目标捆绑。

### 15.4 建议的验证顺序（每步都有停止条件）

1. **最小闭环（约 1 天）**：5.4.8 payload + 现有 Rust 宿主 exe 手工拼一个安装根，把
   `host.local.json` 指到 `versions/<id>/runtime/python/python.exe`，验证 ready、打开真实
   React 工作台、导入库与路线、跑一条路线。跑不通就不必谈身份与安装器。
2. **打包对齐（2–3 天）**：改 `MANAGEMENT_RELEASE`、核对 overlay、生成带 5.4.8 manifest
   的 Setup，装到干净目录，逐项比对 5.4.8 的目录布局与 `installation.json`。
3. **宿主对齐（3–5 天）**：二次启动激活、菜单/托盘/picker/viewer、Quit drain、强制升级
   前先断 agent、首启库安装。
4. **门禁（1–2 周，含用户装机）**：安装 → 首启 → 导入库/路线 → 连服务器 + 强制升级 →
   跑图 → 升级 → 卸载 → 第二台机器；每项对齐 5.4.8 已有证据。

**停止条件**：任一步出现“必须改 Python 管理服务或前端才能通过”，说明不是换壳，应停下
重新界定范围，而不是在宿主里打补丁绕过。
