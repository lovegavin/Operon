## 三、每轮闭环（用户定下的工作流）
1. **主智能体**在本仓库改代码、提交、发布、准备数据与提示词。
2. 每次发行后**覆盖安装**到 `D:\Operon Studio`，主智能体配好 MCP→DSH，然后启动子智能体。
3. 子智能体**只依赖预先写好的提示词 + MCP**跑任务，每次并行少量任务；结果写 `workspace/<task>/`。
4. 子智能体把预期之外的错误按原文报回；主智能体在仓库里批量修复。
5. 攒够一批或子智能体全部完毕 → 改代码 → 提交 → 发布 → 覆盖安装 → 对有问题的任务**新开子智能体**重跑。

## 四、规则（必须遵守）
- 子智能体：只用 `mcp__operon__*`；禁止 ssh、禁止直接调后端 HTTP、禁止改仓库源码、禁止删数据、禁止编造数字；错误原文记录。
- 主智能体：Windows 侧改文件用 `D:\build590\*.py` 脚本（UNC 路径下 DSH 原生文件工具会失败）；远端命令统一走 `D:\build590\rssh.py`；`pkill` 模式必须写成 `operon[.]remote[.]server`、`mmseqs[ ]indexdb` 之类避免自匹配。
- MCP 传输层约 60 s 超时：轮询用 `operon_job(id, wait_seconds<=45)`；`operon_submit` 超时后先用 `operon_jobs`/`operon_job` 复核，不要重复提交。
- `sampling_temp` 必须是字符串；`proteinmpnn_design.device=cpu` 以避免共享 GPU OOM。
- 每次重启桌面后端后，MCP 进程可能缓存旧 build → kill 掉 MCP 进程让 DSH 重启，再 `operon_remote_status(brief=true)` 确认 `build.matches true`。
- `operon_remote_connect` 会返回 ~8 MB catalog，别用它查状态；用 `operon_remote_status(brief=true)`。

## 五、已知缺陷与处置
- **D-35 坐标坍缩（已修 `ade4f7c78`）**：`structure_extract_chain` 写 PDB 时把 mmCIF 的 `Cartn_*` 当缺失，取到常量列 → 靶标坐标全 1.000 → binder 远离靶标 → MPNN 退化同聚物。修复后实测 binder–靶标最小距离 4.2–4.5 Å。
- **D-36 长作业超时（已修 `e76711c51`）**：RFdiffusion 4 设计约 11 分钟，客户端 100 s 就判失败。现 run RPC 1800 s。
- **MPNN CUDA OOM（环境问题）**：共享 GPU 有人在用；子任务一律 `device=cpu`。
- **`.jobs.lock` 残留**：旧 code root 的 `operon.managed_pool` 会持锁导致新守护 `Studio 数据目录正忙`；清理方法 `pkill -f 'operon[.]managed_pool'` + `rm -rf /public/home/lihj/.operon/admission/master/managed-pool`。
- **离线 MSA**：`mmseqs createindex` 在 1.6 TB 余量下不可行（索引 ~1.2 TB、envdb 另需 ~1.5 TB）；目前用公共 `api.colabfold.com`（算子 `msa_host`）已验证可用；AF2 原生 MSA 缺 `alphafold2` 隔离环境，需另行安装。
- **`operon_jobs` 载荷过大（待修）**：返回每个作业的完整 graph/provenance（单次数 MB）。查单个作业用 `operon_job`。
